# 名前解決の精度検証

`docs/ast-plan.md` §11 の検証ハーネス。Stage 2 の受け入れ基準

> import 由来の関係の再現率 ≥ 95%（対 LSP、§11 のレポート） / 検証レポートが CI or スクリプトで再生成できる

を、自リポジトリを対象に実測する。結果は [report.md](./report.md)（生成物。手で編集しない）。

## 実行

```bash
yarn verify:accuracy
```

テストをコンパイルし（`compile-tests`）、`dist/` を作り（`esbuild.js`）、VS Code の拡張機能ホストで
`src/test/astAccuracy.verify.ts` を実行する（`.vscode-test.mjs` の `accuracy` ラベル）。
LSP の参照検索を全シンボルに対して行うため数分かかる。`yarn test`（`integration` ラベル）には含めない。

再現率が基準を下回ると失敗し、終了コードが 0 以外になる。レポートはその場合も書き出す。

## 何をしているか

1. 自リポジトリの TS/JS を、拡張機能と同じ差分キュー（`QueueProcessor`）で調べる。
   1ファイルごとに LSP による従来の関係調査（`table_relationships`）と AST の事実抽出を行い、
   キューが空になった時点で名前解決（`table_relationships_v2`）を行う
2. LSP 由来の関係を正解として、AST 由来の関係を突き合わせる（`src/relationship/accuracy.ts`）
3. `verification/ast-accuracy/report.md` を書き出す

## 突き合わせの方法

両者は参照元・定義の単位が違うため、**言語サーバのシンボルに付いた完全修飾名**へ揃えてから比べる。

| 側 | 参照元・定義の表し方 | 揃え方 |
| -- | -------------------- | ------ |
| LSP | シンボル ID（参照位置を含む最内のシンボル → 定義のシンボル） | 解決キーを持つ最も近い祖先のシンボルの `fqn`（無名コールバックは外側の関数へ） |
| AST | 完全修飾名（出現を囲む最内の定義 → 解決先の定義） | シンボルに付いた `fqn` になるまで、名前の末尾から1段ずつ削る（ローカル変数 → 外側の関数） |

| 指標 | 定義 |
| ---- | ---- |
| **import 由来の関係の再現率** | LSP の関係のうち、定義がトップレベル（`<path>#<名前>` で名前に `.` を含まない）のものを AST が見つけた割合。Stage 2 の受け入れ基準 |
| シンボル単位の再現率（全て） | LSP の全ての関係のうち AST が見つけた割合。`db.query()` のようなインスタンス経由のメンバ参照は Stage 3（型推論）の対象なので、Stage 2 では低い |
| シンボル単位の適合率 | AST のファイル間の関係のうち LSP にもある割合 |
| ファイル単位の再現率・適合率 | 参照元ファイル → 定義ファイルの組で比べた割合。AST は import 関係も含める |

### 比べないもの

- **同じファイル内の関係**: LSP の経路は記録しない（`ref_path !== def_symbol.path`）
- **シンボル単位の import 関係**（ファイル → 取り込んだ定義）: LSP の経路はファイルのルートシンボルを参照元にしないため、
  import 文の位置の参照は記録されない。ファイル単位の比較には含める

### 「import 由来」をこう定義した理由

計画書の基準は「import 由来の関係」とだけ書いている。Stage 2 の名前解決（段1・段2）は名前から定義を引くので、
引ける定義は **import した名前・その名前空間の export・その静的なメンバ**に限られる。インスタンスのメンバ
（`const db = new Db(); db.query()` の `query`）は値の型が分からないと引けず、Stage 3 の対象になる。
そこで「定義がトップレベル」の関係を Stage 2 の守備範囲として測る。全ての関係の再現率も併記する。
