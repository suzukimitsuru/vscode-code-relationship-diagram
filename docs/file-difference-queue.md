# ファイル差分キューと関係調査タスク 仕様

ファイル差分の蓄積（キュー）と関係の調査（タスク）を分離し、
調査をファイル単位で並列実行・中断可能にするための仕様。

---

## 1. 用語定義

| 用語 | 定義 |
| --- | --- |
| **upsert** | 「DBをこのファイルの現状に一致させる」操作。追加と更新を統合したもの。DBに行が無ければ追加相当、在れば更新相当の処理になる（実装側で自動判別） |
| **delete** | 「DBからこのファイルを消す」操作。冪等（存在しない行の削除は無害） |
| **キュー** | `Map<relative_path, { op: upsert \| delete, file }>`。ファイルごとに「望ましい最終状態」を1つだけ保持する |
| **タスク** | 1ファイルのキュー項目を処理する実行単位。計算フェーズとコミットフェーズからなる |
| **シンボルキャッシュ** | **変更ファイルに関係しているファイルだけ**（＝参照検索で実際に見つかった ref_path）のシンボル表を、必要になった時点で読み込むキャッシュ。全ファイルの事前ロードは行わない。enqueue時に該当ファイルを無効化し、キューが空になったら全体をクリアする |

「不変」ファイルはキューに入れない。不変ファイルの役割（参照解決用のシンボル文脈、旧 `_symbol_all`）は
シンボルキャッシュの遅延ロードが担う。必要なファイルは LSP（ReferenceProvider）の応答で初めて判明するため、
事前に全ファイル分を保持する必要は無い。ロード元の選択規則:

- ref_path が**キューまたは実行中タスクに存在する**（＝DBが古い可能性がある）→ 現物からシンボル抽出する
- それ以外 → DBの `symbol_query(ref_path)` から読み込む

---

## 2. 不変条件

1. **キューは1ファイル1エントリ** — 同じファイルの操作は常にマージ（上書き）される
2. **同一ファイルのタスクは同時に1つ** — 実行中のファイルはdequeueしない
3. **DBの codeFile 行はタスク完全成功時のみ更新する** — 途中でクラッシュ・中断しても、次回の差分計算（updated 比較）で自動復旧できる根拠
4. **コミットは直列** — 並列なのは計算フェーズ（シンボル抽出・LSP呼び出し）のみ。DB書き込みは1つずつ順に行う
5. **中断＝計算結果の破棄** — コミット前に中断すればDBは無変更なので、ロールバック機構は不要。コミットフェーズは短時間のため中断対象外

---

## 3. 状態遷移

### 3-1. キューへの追加（enqueue）

**規則: 最後の操作で上書きする（last-write-wins）。**

| キュー \ 新規 | upsert | delete |
| --- | --- | --- |
| （無し） | upsert | delete |
| upsert | upsert（fileを最新に差替え） | delete |
| delete | upsert | delete |

操作が「望ましい最終状態」なので、最新の観測が常に正しい。
旧計画のTODO 2件（削除中の更新／更新中の追加）は「upsertで上書き」に自動解決される。

### 3-2. タスクとの衝突（dequeue時・イベント到着時）

**規則: 実行中タスクがあるファイルに新しい操作が来たら、常にタスクを中断（計算結果を破棄）し、キューに上書き登録する。スケジューラは実行中でないファイルだけをdequeueする。**

ファイル内容が変わった以上、走行中の計算は古い。操作種別に関係なく捨ててやり直すのが常に正しい。

### 3-3. タスクの処理フロー

```text
dequeue（実行中でないファイルのみ、同時実行数の上限あり: 例4）
  ↓
[計算フェーズ]（並列・中断可能）
  upsert: シンボル抽出 → LSPで参照検索 → 参照位置のシンボル表を遅延ロードして突合
  delete: 削除対象の関係・シンボルの特定
  ※中断チェックは await 境界ごと（LSPは即時キャンセル不可のため協調的）
  ↓
[コミットフェーズ]（直列・中断不可・短時間）
  削除（削除シンボル・その関係）→ 関係 → シンボル → codeFile の順にDBへ書き込み
  ↓
参照元ファイルの再調査が必要なら、それらを upsert（全シンボル再調査フラグ付き）としてキューに再投入（fan-out）
```

fan-out の合流規則（fan-out は「ファイル状態の観測」ではなく派生作業なので、通常の enqueue より弱い）:

- キューに delete が登録済み → fan-out は破棄する（削除が最新の観測）
- キューに upsert が登録済み → 再調査フラグを立てるだけ
- 対象ファイルのタスクが実行中 → 中断せず、キューに登録して完了後に実行する
- 実ファイルが存在しない → 破棄する（delete イベント側で処理される）

## 4. シーケンス例

### 例1: 保存の連打

1. `a.ts` 保存 → upsert(a) をenqueue → タスク開始
2. 計算中に再度保存 → タスク中断・結果破棄、upsert(a) を上書き登録
3. タスク終了を検知 → 再dequeue → 最新内容で調査し直す

### 例2: atomic save（delete + create の連続イベント）

1. エディタが一時ファイル経由で保存 → delete(a) イベント → enqueue
2. 直後に create イベント → 表3-1により delete が upsert に上書きされる
3. dequeue時には upsert(a) のみ → 正しく更新として処理される
   （delete タスクが既に走っていた場合も3-2により中断→upsertで再実行）

### 例3: 全走査コマンドと watcher の競合

1. コード関係調査コマンド → 全ファイル走査 → 差分の各ファイルを enqueue
2. 走査結果の処理中にユーザーが `b.ts` を保存 → upsert(b) が上書き登録
3. `b.ts` のタスクが実行中なら中断して再実行、未実行ならキュー上で上書きされるだけ
   → どちらの経路でも最新内容が1回だけ調査される

## 5. 旧計画からの主な変更点

- 操作4種（追加・削除・更新・不変）→ **2種（upsert・delete）** に統合。4×4の遷移表2つが上記の2規則に収束
- 「不変」はキューに入れず、参照先限定のシンボルキャッシュ（遅延ロード）で代替。
  現行の「不変ファイル全件をバッチ毎に読み込む」処理（O(全ファイル)）が、
  「参照が実際に見つかったファイルだけ読む」処理（O(参照先ファイル数)）になる
- ロールバック機構は実装しない。「計算並列・コミット直列」構造により、中断＝結果破棄で足りる
- watcherイベントは該当1ファイルのみをenqueueする（全ワークスペース走査は初回とコマンド実行時のみ）
- 既存の `fileDifference/queue.ts` の `merge()`（バッチ差分マージ）は本設計で不要となり廃止対象

## 6. 検証記録: シンボル抽出とLSP関係調査の並列実行（2026-07-15）

`@vscode/test-electron` 上のサンプルテスト（TypeScript 4ファイルのフィクスチャに対し、
`executeDocumentSymbolProvider` 3件 + `executeReferenceProvider` 3件を逐次/`Promise.all` 並列で発行し比較）で確認した。

検証コードと詳細な記録は [verification/lsp-parallel/](../verification/lsp-parallel/README.md) に保存してある。
再実行はプロジェクトルートから `npx vscode-test --config verification/lsp-parallel/.vscode-test.mjs`。

| round | 逐次 | 並列 | 並列時の重なり合計 |
| --- | --- | --- | --- |
| 1 | 33.8ms | 4.3ms | 13.8ms |
| 2 | 6.1ms | 3.2ms | 11.0ms |
| 3 | 9.7ms | 3.9ms | 12.0ms |

- **並列発行は可能**: エラー・欠落なし。結果（シンボル数・参照数）は逐次実行と完全一致
- **実時間は短縮される**: リクエストが実際に重なって処理され、並列の実時間 < 個別所要時間の合計
- **ただし同一言語サーバー内の意味解析は直列化される**: 参照検索3件の完了時刻は約1msずつ階段状にずれており、
  tsserver 内部でセマンティック要求が順次処理されている。シンボル抽出（構文サーバー）は参照検索と真に並行する
- **含意**: 並列化の利得には言語サーバー側の上限がある。タスク同時実行数の上限（例: 4）は妥当。
  並列化で得るのは主に「往復のオーバーラップ」と「構文系/意味系リクエストの並行」
