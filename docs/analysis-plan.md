# 解析強化・可視化計画

コード関係図を「関係の種類・強さ」「複雑性・認知負荷」を持つ本格的なコード解析ツールへ発展させ、
その情報を全体から詳細まで把握しやすく描画するための3段階の計画。

- **計画1**: ASTを考慮した関係の種類と強さの調査・DuckDB保存
- **計画2**: コードの複雑性と認知負荷の調査・DuckDB保存
- **計画3**: 計画1・2のデータを活用した「全体から詳細まで」把握しやすい描画

---

## 現状の整理（前提）

### データモデル（`src/codeDb.ts`）

```sql
table_files         (relative_path PK, language_id, updated_at)
table_symbols       (id PK, parent_id, name, kind, path, define/start/end位置, hash)
table_relationships (reference_id, define_id)   -- 種類・強さの情報なし
```

### 関係抽出（`src/relationship/codeRelationships.ts`）

- VSCode `executeReferenceProvider` で参照位置を取得し、`findSymbol()` で参照元シンボルを特定
- 得られるのは「参照 → 定義」のペアのみ。**関係の種類（呼び出し/継承/import等）や強さは判別していない**

### 保守性スコア（`src/relationship/cosmosAdapter.ts`）

- `maintenanceScore` は in/out-degree・行数などのグラフ構造ヒューリスティックで算出
- **コード内部の複雑性（分岐・ネスト等）は考慮していない**

### 課題

1. すべての関係線が同じ意味に見える（importも継承も呼び出しも同じ線）
2. 「保守性」がコードの中身を反映していない
3. 大規模グラフで全体像と詳細の行き来が難しい（ノード数が多いと均質な点の集まりに見える）

## 計画1: ASTを考慮した関係の種類と強さの調査・DuckDB保存

### 1.1 目的

関係 `(reference → define)` に **種類（kind）** と **強さ（strength）** を付与し、
「どのように依存しているか」「どれだけ強く依存しているか」を分析・描画できるようにする。

### 1.2 AST取得方式の選定

| 方式 | 対応言語 | 精度 | 備考 |
| ---- | -------- | ---- | ---- |
| **tree-sitter（web-tree-sitter/WASM）** | 多言語（TS/JS/Python/Go/Rust/C#…） | 構文レベル | **採用案**。言語ごとにWASM文法を同梱 |
| TypeScript Compiler API | TS/JSのみ | 型情報まで高精度 | TS/JS専用の精度向上オプションとして併用可 |
| VSCode Semantic Tokens | LSP依存 | トークン分類のみ | 構文木が取れないため不採用 |

**方針**: 言語非依存の基盤として tree-sitter を採用し、文法未対応言語は
既存のReferenceProviderベースの抽出結果（種類= `unknown`）にフォールバックする。

### 1.3 関係の種類（taxonomy）

`RelationshipKind` として整数enumで定義し、DBに保存する。

| kind | 名称 | 判定方法（ASTノード例: TS） | 基本重み |
| ---- | ---- | --------------------------- | -------- |
| 1 | `import` | import文 / require呼び出し | 1 |
| 2 | `inheritance` | `extends` 句 | 10 |
| 3 | `implementation` | `implements` 句 | 8 |
| 4 | `instantiation` | `new` 式 | 5 |
| 5 | `call` | 関数・メソッド呼び出し式 | 3 |
| 6 | `type_reference` | 型注釈・ジェネリクス引数 | 2 |
| 7 | `read` | 変数・プロパティ読み取り | 1 |
| 8 | `write` | 変数・プロパティへの代入 | 4 |
| 9 | `decorator` | デコレータ適用 | 5 |
| 0 | `unknown` | AST判定不能（フォールバック） | 1 |

**判定ロジック**: ReferenceProviderが返した参照位置に対し、その位置を包含する
ASTノードの祖先を辿って種類を判定する（例: 参照位置が `new X()` の `X` なら `instantiation`）。
既存の抽出フローを置き換えるのではなく、**参照位置に種類を注釈する**構成にする。

### 1.4 関係の強さ（strength）

2層で保持する。

1. **出現単位（raw）**: 1参照 = 1行として `table_relationships` に kind・行位置付きで保存
2. **集約単位（aggregated）**: シンボルペア/ファイルペアごとに
   `strength = Σ(kind別の基本重み × 出現回数)` を正規化（log圧縮 + 最大値スケーリング）

集約はDuckDBのSQL（`GROUP BY` + `SUM`）で行い、VIEWとして定義する（保存処理の単純化と再計算容易性のため）。

### 1.5 スキーマ変更

```sql
-- スキーマバージョン管理（マイグレーション用に新設）
CREATE TABLE IF NOT EXISTS table_schema_version (version INTEGER);

-- 関係テーブルを拡張（v2）
CREATE TABLE IF NOT EXISTS table_relationships (
    reference_id   TEXT,
    define_id      TEXT,
    kind           INTEGER DEFAULT 0,   -- RelationshipKind
    weight         REAL    DEFAULT 1.0, -- kind別基本重み（調整可能に保存）
    reference_line INTEGER              -- 参照出現行（詳細表示・ジャンプ用）
);

-- 集約ビュー
CREATE OR REPLACE VIEW view_relationship_strength AS
SELECT reference_id, define_id, kind,
       COUNT(*)     AS occurrence_count,
       SUM(weight)  AS strength
FROM table_relationships
GROUP BY reference_id, define_id, kind;
```

**マイグレーション**: 起動時に `table_schema_version` を確認し、旧スキーマなら
`ALTER TABLE ... ADD COLUMN` で拡張（既存行は `kind=0, weight=1.0`）。
再調査（examineRelationships）で順次正しい種類に置き換わる。

### 1.6 実装ステップ

| # | 作業 | 対象ファイル |
| - | ---- | ------------ |
| 1 | `web-tree-sitter` 導入・言語WASMのバンドル（まずTS/JS） | `package.json`, `esbuild.js` |
| 2 | ASTサービス新設: パース・位置→ノード解決・種類判定 | `src/extruct/ast/astService.ts`（新規）, `src/extruct/ast/kindClassifier.ts`（新規） |
| 3 | `Relationship` モデルに `kind`/`weight`/`referenceLine` を追加 | `src/relationship/codeRelationships.ts` |
| 4 | `examine()` で参照位置ごとに種類を注釈 | `src/relationship/codeRelationships.ts` |
| 5 | スキーマv2・マイグレーション・集約ビュー | `src/codeDb.ts` |
| 6 | 保存/読込APIの拡張（`relationship_inserts` 等） | `src/codeDb.ts`, `src/relationship/examine.ts` |
| 7 | 言語追加（Python/Go 等、需要順） | `src/extruct/ast/` |

### 1.7 リスクと対策

- **WASMサイズ増**: 言語WASMは遅延ロード（対象ファイルの language_id 出現時のみ）
- **AST位置とProviderの位置ズレ**: 判定不能時は `unknown` にフォールバックし、既存動作を維持
- **パース時間**: 差分処理（`FileDifferenceQueueProcessor`）に統合し、変更ファイルのみ再パース
- **既存DBとの互換**: スキーマバージョンで移行。移行失敗時は再構築を案内

## 計画2: コードの複雑性と認知負荷の調査・DuckDB保存

### 2.1 目的

シンボル単位・ファイル単位でコードの複雑性指標を計測して保存し、
現在グラフ構造のみで算出している `maintenanceScore` を実際のコード内容に基づく指標へ置き換える。

### 2.2 計測する指標

計画1のASTインフラ（tree-sitter）を共用して算出する。

| 指標 | 内容 | 算出方法 |
| ---- | ---- | -------- |
| **循環的複雑度**（cyclomatic） | 分岐数ベースの経路複雑性 | `if/for/while/case/catch/&&/\|\|/?:` ノード数 + 1 |
| **認知的複雑度**（cognitive） | 人間の読解負荷（SonarSource方式） | 分岐 +1、**ネストごとに加算増**、再帰 +1、フロー中断（break/continue/goto）+1 |
| 最大ネスト深度 | 制御構造の最深段数 | AST走査 |
| パラメータ数 | 関数の引数の数 | ASTノード |
| 実行行数（LOC） | コメント・空行を除く行数 | ASTノード範囲 |
| Halstead Volume（任意） | 演算子・被演算子の語彙量 | 第2段階で追加検討 |
| **保守性指数**（MI） | 上記の合成指標（0-100） | `171 - 5.2*ln(HV) - 0.23*CC - 16.2*ln(LOC)` を正規化（HV未実装時は簡易式） |

**集約**: ファイル値 = 所属シンボルの最大値・合計・加重平均（行数重み）を併記して保存。
「1つの巨大関数」と「多数の小さい関数」を区別できるようにする。

### 2.3 スキーマ追加

```sql
-- シンボル単位のメトリクス（v3）
CREATE TABLE IF NOT EXISTS table_metrics (
    symbol_id            TEXT PRIMARY KEY,  -- table_symbols.id
    path                 TEXT,              -- 削除時の一括処理用
    cyclomatic           INTEGER,
    cognitive            INTEGER,
    max_nesting          INTEGER,
    parameter_count      INTEGER,
    lines_of_code        INTEGER,
    halstead_volume      REAL,              -- 未算出時 NULL
    maintainability      REAL,              -- 0-100
    computed_at          TIMESTAMP
);
CREATE INDEX IF NOT EXISTS idx_metrics_path ON table_metrics(path);

-- ファイル単位の集約ビュー
CREATE OR REPLACE VIEW view_file_metrics AS
SELECT path,
       MAX(cognitive)            AS max_cognitive,
       SUM(cognitive)            AS total_cognitive,
       MAX(cyclomatic)           AS max_cyclomatic,
       SUM(lines_of_code)        AS total_loc,
       MIN(maintainability)      AS worst_maintainability
FROM table_metrics
GROUP BY path;
```

### 2.4 差分処理への統合

シンボルの `hash` が変わったときだけ再計測する（既存の差分分配 `distribute` と同じ思想）。

```text
FileDifferenceQueueProcessor の処理フローに組み込む:
  fileAdditions/fileUpdates でシンボル抽出
    ↓ 同じ TextDocument から AST をパース（計画1と1回のパースを共有）
    ↓ シンボル範囲ごとにメトリクス算出
    ↓ examine.processes に table_metrics の upsert を追加
  fileRemoves で table_metrics も削除
```

### 2.5 実装ステップ

| # | 作業 | 対象ファイル |
| - | ---- | ------------ |
| 1 | メトリクス計算器（AST走査で全指標を1パス算出） | `src/extruct/ast/metrics.ts`（新規） |
| 2 | スキーマv3・`metrics_upsert/query/deleteFile` API | `src/codeDb.ts` |
| 3 | 差分処理へ組み込み（hash変更時のみ再計測） | `src/relationship/examine.ts` |
| 4 | `showDiagram` 読込にメトリクスを追加 | `src/extension.ts`, `src/relationship/visualization.ts` |
| 5 | `maintenanceScore` を実メトリクス（MI）ベースへ置換¥n（グラフ構造スコアは補正項として残す） | `src/relationship/cosmosAdapter.ts` |

### 2.6 リスクと対策

- **言語ごとの構文差**: 制御構造ノード名を言語別マッピングテーブルで吸収。未対応言語はLOCのみ保存
- **計測時間**: 計画1とパースを共有し追加コストをAST走査1回に抑える
- **指標の妥当性**: 認知的複雑度はSonarSourceの公開仕様に準拠し、テストコードで検証

## 計画3: 全体から詳細まで把握しやすい描画

### 3.1 目的（計画1・2の実装後）

関係の種類・強さ、複雑性・認知負荷のデータを使い、
**俯瞰（全体アーキテクチャ）→ 中間（モジュール間依存）→ 詳細（シンボル単位）** を
シームレスに行き来できる可視化にする。

本計画は現行実装（BFS同心円レイアウト + 力学シミュレーション）の延長線ではなく、
現状の描画の問題（§3.2）を起点に**ゼロベースで描画方式を再設計**する。

### 3.2 現状の描画の問題点

現行描画（`docs/diagram-specs.md`: BFS同心円 + 力学シミュレーション）には、
「全体から詳細まで」の把握を妨げる次の問題がある。

| # | 問題 | 原因 |
| - | ---- | ---- |
| 1 | **俯瞰してもコードの構造が見えない** | 位置を決めるBFS深度は「エントリポイントからの参照距離」であり、ディレクトリ/モジュール構造と一致しない。同じディレクトリのファイルがリング上に散らばり、アーキテクチャの単位が図に現れない |
| 2 | **粒度が2段階（ファイル/シンボル）しかない** | 中間の集約層（ディレクトリ・モジュール）がなく、数千ファイルでは俯瞰が均質な点の集まりになる。ズームは幾何拡大のみで、拡大しても情報の粒度が変わらない |
| 3 | **リング上の角度位置に意味がない** | 同一リング内の並びは被参照数順のため、関連の深いファイル同士が円周上で離れ、エッジが円を横断して長距離・交差だらけになる（ヘアボール化） |
| 4 | **エッジが束ねられず幹線が見えない** | 全エッジを個別の直線で描くため、依存の「太い流れ」（どのモジュールがどのモジュールに依存しているか）が視覚的に浮かび上がらない |
| 5 | **レイアウトが非決定的** | 力学シミュレーションの結果が実行ごとに変わり、「前に見たあの場所」という空間記憶が使えない。Living Document として繰り返し参照する用途に不向き |
| 6 | **配置ルールが複雑で位置から意味を読めない** | サブリングあふれ・複数エントリポイントの平均深度・孤立ノード最外周などのルールは、見る側が位置から意味を復元できない |
| 7 | **どこを見るべきかの誘導がない** | 俯瞰時に問題領域（低保守性・高複雑度）が集約されて見えず、ラベルも重なって読めないため、詳細へ降りる手がかりがない |
| 8 | **全体↔詳細の往復手段が乏しい** | ミニマップ・パンくず・ドリルダウンがなく、行き来はズーム/パン操作のみ。深度スライダーは表示を削るだけで「隠れているものの存在」の文脈を失う |

### 3.3 設計原則

既存実装を前提とせず、次の原則で設計し直す。

1. **Overview first, zoom and filter, details on demand**（Shneiderman の視覚情報探索原則）
2. **視覚変数の役割を固定する**:
   - **位置** = 構造（どこに属するか）
   - **大きさ** = 規模（行数・内包数）
   - **色** = 品質（保守性・複雑度、計画2のデータ）
   - **線** = 依存（種類・強さ、計画1のデータ）
   - 1つの視覚変数に複数の意味を持たせない
3. **決定的レイアウト**: 同じコードからは常に同じ図が得られ、コード変更時は変更箇所だけが動く（空間記憶の維持）
4. **どのズーム倍率でも読める**: すべてのズームレベルで、その粒度に応じたラベルと集約値が読み取れる（セマンティックズーム）

### 3.4 レイアウト: 入れ子円パッキング（構造 = 位置）

「位置」をディレクトリ階層で決める。BFS同心円・力学シミュレーションは廃止する。

```text
ワークスペース（最外円）
 └─ ディレクトリ（入れ子の円）
     └─ ファイル（円）
         └─ シンボル（ファイル円の内部の円）
```

- **包含関係がそのまま視覚的包含になる**: 「circleAの中にcircleBがある」=「AディレクトリにBが属する」。
  凡例なしで構造が読める
- 円内の子要素の配置は**決定的な円パッキング**（子を名前順に並べて詰める）で事前計算する。
  実行ごとに変わらず、ファイル追加時も既存要素の相対位置がほぼ保たれる
- 参照関係は位置に影響させず、**線でのみ**表現する（構造と参照の分離。問題1・3・5・6の解消）
- エントリポイントはバッジ（◎マーク等）で識別し、BFS深度は詳細パネルの属性情報として残す
- Louvainコミュニティは位置ではなく「コミュニティ境界線オーバーレイ」（同一コミュニティを囲む淡い輪郭）として任意表示にする

### 3.5 セマンティックズーム（LOD: Level of Detail）

ズーム倍率ではなく「**画面上での円の直径**」を基準に、円ごとに展開/集約を判定する。

| 状態 | 判定 | 表示 |
| ---- | ---- | ---- |
| 集約 | 画面上の直径 < 展開閾値（例: 80px） | 円1つ + 名前 + 集約バッジ（内包ファイル数・最悪保守性色） |
| 展開 | 画面上の直径 ≥ 展開閾値 | 内部の子円（ディレクトリ→ファイル→シンボル）を描画 |

- 判定が円ごとの局所ルールなので、**画面内で粒度が混在する**:
  注視している領域だけが深く展開され、周辺は集約されたまま残る。
  「全体の文脈を保ったまま一部を詳細に見る」が単一のビューで成立する（問題2・8の解消）
- エッジも同じ規則で集約する: 両端のうち「画面に見えている最深の祖先円」同士の集約エッジとして描画。
  ズームインすると集約エッジが個別エッジへ分解されていく
- 展開/集約の切替はフェードで連続的に行い、視線の追従を保つ

### 3.6 エッジ表現（計画1のデータ）

| データ | 視覚表現 |
| ------ | -------- |
| 種類（kind） | エッジ色（例: import=グレー、継承=紫、呼び出し=青、書き込み=赤系） |
| 強さ（strength） | エッジ幅（logスケール）+ 不透明度 |
| 集約エッジ | 内包する個別エッジの strength 合計を幅に反映（モジュール間の「幹線」が太く見える） |
| 経路 | **階層エッジバンドリング**: エッジを円階層の共通祖先経由の曲線で描き、同方向の依存を束ねる（問題4の解消） |

フィルタ:

- **kindトグル群**（「継承だけ表示」「import非表示」等）
- **strength閾値スライダー**（弱い依存を消して幹線だけ残す。全体把握の主力機能）
- **選択時個別表示**: 非選択時は集約幹線のみ描き、ノード選択時にそのノードの個別エッジを重ね描きする（常時全エッジ描画をやめ、ヘアボールを構造的に回避）

### 3.7 色・ラベル（計画2のデータ）

| データ | 視覚表現 |
| ------ | -------- |
| 保守性指数 | ノード色（実メトリクス駆動） |
| 認知的複雑度 | **ヒートマップモード**: 複雑度で色付けするカラーモード切替 |
| ワースト集約 | 集約円の色 = 内包シンボルの最悪値。**ズームアウトしても問題領域が赤く見え、ドリルダウンの誘導になる**（問題7の解消） |
| Dead code / 循環参照 | 現行同様のハイライトを維持（円の縁取り色） |

- カラーモードは「保守性 / 複雑性ヒートマップ / コミュニティ」の3択トグル
- ラベルはLOD連動: 円が読める大きさ（例: 直径40px以上）のときのみ描画。俯瞰時はトップレベルディレクトリ名だけが読める状態を保証する

### 3.8 ナビゲーション

1. **ドリルダウン/アップ**: 円のダブルクリックでその円が画面に収まるまでズーム（=自動的に1階層展開）。背景ダブルクリックで1階層上へ
2. **パンくず表示**: 現在の注視階層（workspace > dir > file > symbol）を表示、クリックでその階層へズームバック
3. **ミニマップ**: 右下に最外円の縮小図 + 現在ビューポート枠。クリックでジャンプ
4. **ワーストランキングパネル**: 認知負荷・保守性ワースト上位N件のリスト → クリックで該当円へズーム
5. **依存トレース**: ノード選択時に上流/下流を段階的にハイライト（深さ1→2→3とキーで拡張）。トレース対象外は減光
6. **コードジャンプ**: シンボル円のクリックで該当ファイル・行をエディタで開く（Living Document 要件）
7. **検索**: 名前インクリメンタル検索 → 該当円へズーム

### 3.9 実装ステップ

レイアウトエンジンとLOD管理を新規モジュールとして実装し、現行描画は完成まで並存させる。

**レンダラー選定**: Cosmos.gl は点群+直線エッジのGPUレンダラーであり、入れ子円・バンドリング曲線・
LOD混在描画には適合しない。ステップ3で以下を比較検証して決定する。

- 候補A: Canvas 2D + ビューポートカリング（実装が単純。LODで描画数を絞れるため数万ノードでも成立する見込み）
- 候補B: WebGL自前描画（PixiJS / regl 等。Canvas 2D で性能不足の場合）

### 3.10 パフォーマンス方針

- **LODが第一のパフォーマンス機構**: 同時描画数は「画面に見えている展開済みの円 + 集約エッジ」のみ。
  俯瞰時は数十〜数百要素、ズームイン時もビューポートカリングで同オーダーに収まる
- レイアウト（円パッキング座標）はExtension側で事前計算し、既存のチャンク転送でWebviewへ送る
- 円パッキングは階層ごとに独立計算できるため、コード変更時は**変更のあったディレクトリ配下のみ再パック**する差分更新が可能
- 力学シミュレーションの廃止により、描画時の計算はズーム・LOD判定・フェードのみになる
